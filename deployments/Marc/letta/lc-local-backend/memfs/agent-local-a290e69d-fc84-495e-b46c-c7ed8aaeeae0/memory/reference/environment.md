## Per-agent MCP write interface (fleet-wide, verified 2026-09-25)
The operator added a **per-agent MCP "write" service** to the whole fleet ("write shit on the golem's forehead") — every agent now exposes its own ClusterIP service `<name>-mcp` (port 8000), backed by a **FastMCP HTTP server running inside each pod** that lets you pipe a prompt straight into that agent and read its reply.

- **Naming/convention:** each agent gets a `sudo-<name>-mcp` ClusterIP service (port `8000` → targetPort = a per-pod nodePort, e.g. psnvc's is `27755`). Selector is `agent: <name>, app: sudo-<agent-kinds>`. There is one service **per agent**, not per pair (so `-l` and `-h` each get their own).
- **Server:** a thin FastMCP wrapper at `/opt/letta-mcp/` in each sudo-letta pod (`mcp_server.py` + `letta_prompt.py` + `mcp_entrypoint.sh`). It serves **streamable HTTP (MCP-over-HTTP)** on `/mcp` — NOT a plain REST server, so `GET /` and `/openapi.json` and `/docs` all return 404; the real route is `/mcp` and it speaks the MCP JSON-RPC initialize → `tools/list` → `tools/call` flow (returns an `mcp-session-id` header to use on follow-up calls).
- **Write tool per agent kind:**
  - **Letta agents** → single tool `letta_prompt(prompt, json=false, new_chat=false, mode, source)` — maps 1:1 to `letta-p.py` flags; invokes the Letta CLI *directly against its own pod* (no kubectl/kubeconfig). (The `stream` flag was dropped 2026-09-28 — see Redis queue note below.)
  - **Hermes agents** → `hermes_prompt(prompt, json)` (same idea, one-shot).
- **Handshake facts:** `initialize` returns `sudo-letta` v4.0.9, MCP protocol `2025-03-26`, with `tools` capability. The tool's `inputSchema` exposes the four flags above; a real agent turn spins up on `tools/call` (takes seconds to generate — the CLI invocation is not instant).
- **Two design limits (both intentional):**
  1. **One-shot / resume-by-default** — no live streamed deltas over MCP; `new_chat=true` forces `--new`, otherwise it resumes the agent's persisted conversation (via `settings.json` conversation id).
  2. **No cross-agent routing from inside a pod** — each pod's MCP can only write to *its own* agent. Cross-agent name resolution (`letta-p.py --list`) is host-side only (needs kubectl/kubeconfig); it is deliberately NOT exposed in-pod.
- **Self-call gotcha:** writing to *yourself* (`sudo-psnvc-mcp` → `letta_prompt`) works but is inherently recursive — a clean test targets any *other* agent.
- **Reaching it:** from inside the VM, `curl http://192.168.5.15:<nodePort>/mcp` (or `wget` with `--post-data`); the host LAN IP `192.168.5.15` is reachable inside the VM but NOT from the Mac browser without a port forward (same Lima boundary as the rest of 8000).
- **Working recipe (verified live 2026-09-25, reach → mail-bot-letta at nodePort `18965`):** `initialize` POST to `/mcp` → capture `mcp-session-id` header → `tools/call` the `letta_prompt`/`hermes_prompt` tool. The reply lands in the SSE stream as `result.content[0].text` (mirrored in `result.structuredContent.result`). Proven non-recursively against mail-bot-letta ("Hey psnvc! 👋") and forge via `hermes_prompt` ("Hello psnvc — forge here…") — so this is now THE clean way to message any agent, replacing the kubectl/docker/nsenter bridge for one-shot prompts.

**Queue semantics (implemented in `mcp_server.py` in both factories):**
- Enqueue → **single drain worker** feeds the agent **one prompt at a time** — N rapid prompts = N *queued* runs, never N parallel races.
- **Ordering:** (a) FIFO by arrival, (b) then drain ALL remaining from the *same `source`* before anyone else, (c) else next most-recent source, (d) FIFO within source.
- **Two delivery modes:** `direct` (enqueue + wait for result, no timeout) and `inbox` (enqueue, return a message id immediately, fetch later).
- **Params:** `source` tag enables group-by-source ordering. Observability window = `letta_queue_status()` / `hermes_queue_status()` (pending + recent results).
- **Engineer `hermes_prompt`** = `prompt, json, mode, source` only — **no `stream`/`new_chat`** (Hermes is stateless; those are no-ops). Planner `letta_prompt` carries `json`/`new_chat`/`mode`/`source`.
- **`stream` flag DROPPED from `message-agent`/`letta_prompt` (2026-09-28, operator decision).** The `stream` flag was removed because it was redundant and half-built: `direct` mode already returns the full reply string, and token-level streaming is pointless for a synchronous send→reply tool — a long job should use `mode="inbox"` + `queue_status` polling instead of streamed deltas. It was also planner-only (ignored for engineers) and its only function ("join deltas into one reply") was already the default behavior. forge removed it across the four files (feature, contract, `comm_tools.py` interface, tests). So the settled planner surface is `(prompt, new_chat, json, mode, source)` — no `stream`.

## How to make the four comm tools — build them as MCP CLIENTS, not new servers (RESOLVED 2026-09-27)
This is the answer to "how do we make a tool". The four comm tools (`list-siblings`, `message-agent`, `check-what-agent-is-doing`, `check-agent-logs`) should be built as **MCP CLIENTS**, not new servers. The research-backed decision rule (three criteria):
- **(a)** the target already has a stable API (the `-mcp`/`-watch` sidecars) → use function-calling/MCP;
- **(b)** used fleet-wide → MCP, not per-agent;
- **(c)** the agent IS a CLI-with-shell → call existing CLIs from bash, don't build a tool layer.

So concretely: `message-agent` ≈ an MCP client that calls a sibling's `letta_prompt`/`hermes_prompt`; `check-what-agent-is-doing` ≈ `GET -watch/status`; `check-agent-logs` ≈ `GET -watch/events`.

**Comm-tool interface details (reviewed 2026-09-28 against the live `comm_tools.py` + gherkin feature/contract/test files, while writing the per-tool skills):**
- **`list_siblings(filter=None, *, fleet)`** — one optional `filter` (substring on the bare name; unique→one entry, multiple→all, no-match→empty `[]`, never error/hang) plus the injected `fleet` dependency. Returns the whole live fleet as `[{sibling, mcp_host, watch_host}]`. Roster is **live** (re-runs `kubectl get services` every call, never cached).
- **`message_agent(sibling, prompt, mode="direct", new_chat=False, json=False, source=None, fleet=fleet)`** — `sibling`+`prompt` are required; the rest are flags. `mode` = `direct` (send+wait) vs `inbox` (return id immediately, fetch later via `queue_status`). Name resolution: exact → case-insensitive → unique-substring → ambiguous (lists candidates) → not-found. Planner/engineer split: `json=True` returns a JSON object for planners but a pretty-printed string for engineers (an asymmetry flagged as an open "is this what we want" question). **`stream` was DROPPED (2026-09-28)** — redundant with `direct`, planner-only, half-built (removed from the signature).
- **`check-what-agent-is-doing(..., facet="status", fleet=fleet)`** — one optional flag `facet`: `"status"` (default → `GET /status`, a 10-field snapshot `{agent, deploy, uptime_s, agent_container_up, active, current_conversation, last_event_ts, events_logged, transcript_bytes, watch_port}`) vs `"processes"` (→ `GET /ps`, `{pid, ppid, uid, age_s, cmdline}`). **Contract inconsistency flagged:** the CONTRACT.md says it returns a distilled 5-field set, but the feature + tests say the full 10-field `/status` snapshot; recommendation (open) is to return the full snapshot (the "is it alive" scenario needs `agent_container_up`, which the 5-field contract omits).

## Per-agent `watch` observability sidecar (fleet-wide, discovered 2026-09-27 — NOT in the ledger)

- **Pod wiring:** the `watch` container mounts the **same PVC** (`data` → `/home/node/.letta`, so it shares the agent's memory/state), plus a per-agent **ConfigMap** `sudo-<name>-watch-config` at `/etc/watch-config`. - **ConfigMap `config.json`** (per agent): `{"agent_name","deploy_name","watch_port","poll_interval_sec":2,"log_dir":"/home/node/.letta/watch"}`. `watch_port` is **deterministic per agent** (psnvc = 16253, same `8642 + cksum(name)%5000` family).
- **What it does:** continuously tails the agent's own conversation logs (`~/.letta/lc-local-backend/conversations/*/messages.jsonl`) and re-emits a structured event stream — each turn flattened to `{"ts","conversation","event","text"/"name","args"}` — polled every 2s, written to `~/.letta/watch/`:
  - `events.jsonl` — append-only event log (13.8MB and growing)
  - `state.json` — rolling snapshot mapping every `messages.jsonl` file (base64-ID) → byte offset (diffs file sizes to detect new activity)
  - `transcript.txt` — rendered transcript
- **It watches ME live:** psnvc's own turns (e.g. `conversation:local-conv-18`) appear in its `events.jsonl` as they happen.
- **Network surface:** each agent also gets a `sudo-<name>-watch` ClusterIP Service (port 8000 → the per-agent `watch_port`), so the stream is network-reachable. The HTTP server identifies as **`letta-watch/1.0` Python 3.11.2** — root `/` returns 404 `not found` (real routes are elsewhere; not yet mapped).

## `stream.sh` — the operator's live event-stream reader (discovered/used 2026-09-27)
The operator's newest monitor tool, at `/opt/0-0/sudo-agent/kube-scripts/stream.sh` (and `/opt/0-0/sudo-letta/kube-scripts/stream.sh`). It reads the `watch` sidecar's `events.jsonl` directly via `kubectl exec ... tail -f` (no HTTP, no port-forward) and pretty-prints **one line per event** — `TYPE: first line`, where `TYPE ∈ {USER, THINKING, ASSISTANT, TOOL, RESULT, SESSION, PROC}` (machine self-prompt events render `SYS>`; `TOOL` lines show tool name + short args; lines truncate ~200 chars).

## Letta one-shot process shape + the `agent-watch.sh` monitor blind spot (verified 2026-09-25)

## Hermes per-agent config (`config/<name>.yaml`) — what's actually in it (verified 2026-08-25)

Each Hermes agent mounts its own `config/<name>.yaml` (host path `/opt/0-0/sudo-agent/config/<name>.yaml`) → `/opt/data/config.yaml` in the pod. Content of one (fa-glm-h) is the template plus ONE added block:

```yaml
model: { default: "deepseek-v4-pro", provider: "deepseek" }
terminal: { backend: "local", sudo_password_env: "SUDO_PASSWORD" }
memory:
  memory_char_limit: 100000
  user_char_limit: 50000
  memory_enabled: true
  user_profile_enabled: true
  write_approval: false
  nudge_interval: 1
display:
  skin: fa-glm-h            # ← the ONLY per-agent delta baked in so far
```

So as of 2026-08-25, the *only* thing actually differing between any two Hermes agents' configs is `display.skin` (the CLI display name/banner). The value is the *capability now unlocked*, not current divergence. **Secrets (API key + sudo password) are NOT in this YAML** — they're inlined plaintext in `deployments/<name>.yaml` `env:` (a known issue).

### What's tunable per-agent now (forge's inventory of the live install, Hermes v0.20.4)
High-value, direct keys:
- `model.default` / `model.provider` — run each agent on a different model (the big one).
- `agent.reasoning_effort` — how hard each agent thinks (low/medium/high/max). See `--reasoning` below.
- `agent.max_turns` / `run_budget_seconds` — cap loop length.
- `agent.disabled_toolsets` — prune which tools an agent gets.
- `memory.*` (limits, `memory_enabled`, `write_approval`) — size, on/off, auto-approve writes.
- `delegation.*` — subagent auto-approve / spawn depth.
- `approvals.mode` — command-approval posture per agent.
- `display.skin` + `skins/<name>.yaml` — name, welcome text, colors, spinner, per-tool emoji, ASCII banner, `branding.*` (agent_name), response_label.
- `terminal.backend` — per-agent execution backend.
- `fallback_providers` — per-agent failover chain.

"Unknown avenues" forge surfaced (deeper/less-covered):
- **Credential pools** (`hermes auth`) — rotate across multiple API keys, isolating rate limits per agent.
- **MoA presets** (Mixture-of-Agents) — different reference models + aggregator per agent.
- **Custom providers** — declare OpenAI-compatible endpoints.
- **Profiles** (`hermes profile`) — fully isolated config/session/memory per profile (built-in sharding).
- **Hooks** (`hooks {}`) — arbitrary shell scripts on `pre_tool_call` / `post_llm_call` etc.
- **Ephemeral prompt injection** (`HERMES_EPHEMERAL_SYSTEM_PROMPT`, `prefill_messages_file`) — inject non-persistent context.

### Reasoning effort control (verified 2026-08-25 by forge — LIMA box build ONLY)
- `hermes chat --reasoning <level>` — real flag, overrides for a single session. Levels: `none, minimal, low, medium, high, xhigh, max, ultra`.
- `agent.reasoning_effort` — the persistent per-agent config key (`hermes config set agent.reasoning_effort <level>`, or directly in `config/<name>.yaml`). There's also `agent.reasoning_overrides` (per-model dict, spelling-tolerant) that takes precedence.
- **⚠ Box-scoped (learned 2026-08-26 on fabean):** these `--reasoning`/`agent.reasoning_effort` controls were verified on the **lima** host's Hermes build. On **fabean's** Hermes build (v0.20.4 running a LiteLLM `provider: custom` model like ioi-h), **neither `hermes chat --reasoning` nor `agent.reasoning_effort` exists** — the only knob that raises/lowers "how hard it thinks" is **model selection** (pick a different LiteLLM alias via `hermes -z -m <model> ...`). Before baking reasoning guidance into a persona, verify WHICH box the engineer runs on and whether its build actually has the flag — don't assume both boxes match.
- **Gap:** `talk.sh` runs `kubectl exec -it deploy/sudo-<name> -- hermes` with NO flag pass-through — so `--reasoning` cannot be passed through `talk.sh`. Dynamic per-task reasoning would require invoking `hermes -z "<prompt>" --reasoning <level>` directly through the host bridge. Static default = easy; dynamic = needs that raw invocation (or a `talk.sh` mod to forward `"$@"`).

### Hermes skills/plugins (verified 2026-08-25)
- Mechanism: a skill is a folder with `SKILL.md` + optional scripts, loaded into agent context *when relevant*. It does NOT add model "muscle" — it adds procedural knowledge + run-recipe specificity. Value scales with how non-obvious the knowledge is (high value for exact commands/getchas/env specifics; ~zero for base-model-known stuff like "what is systemd").
- The built-in `skills/` + `optional-skills/` trees are **thin on Linux server ops** — there is **no dedicated systemd, k8s, or SSH skill**. Server-ops muscle comes from the SOUL's embedded knowledge + base model, not a skill.
- Relevant installable skills for a server-shell agent like fa-glm-h: `docker-management` (devops), `systematic-debugging` (software-development, 4-phase root-cause), `web-pentest` (security), `pinggy-tunnel` (devops, expose services), `watchers` (devops, poll/monitor); optionally `serving-llms-vllm`/`llama-cpp` if serving models.
- Install/enable commands: `hermes skills install <ID>`, `hermes skills browse/search`, `hermes skills config` (enable/disable), `hermes plugins install <owner/repo>` + `hermes plugins enable <name>`, `hermes bundles create` (bundle several under one alias). Skills live in `$HERMES_HOME/skills/` (= `/opt/data/skills/` in the pod); built-in/optional trees are in the source tree `/opt/hermes/` and get seeded/copied into the profile.
- **Skill-authoring tooling (verified 2026-08-25):** `hermes-agent-skill-authoring` skill (category `software-development`) is preloaded on forge — it's the meta "how to write good Hermes skills" skill (frontmatter schema, 60-char description hardline, tier decision, body section order, platform gating, size limits, a 10-item pitfalls list). Backed by tooling: `skill_view(name='hermes-agent-skill-authoring')` to load it; `python -m tools.skill_linter <SKILL.md|dir>` to lint a skill (forge verified it works live); `hermes skills publish <path> --to {github,clawhub} --repo <repo>` to package. The CLI has **no** `create`/`new`/`init`/`scaffold` subcommand (only publish + snap etc.).
- **Letta skills ≠ Hermes skills (confirmed 2026-08-25):** same *concept* (a `SKILL.md` of procedural knowledge loaded on demand), different format + discovery. Hermes frontmatter = `name`/`description`/`version`/`author`/`license`/`platforms`/`metadata.hermes`; Letta frontmatter = just `name` + `description`. Hermes discovers skills in `$HERMES_HOME/skills/` (= `/opt/data/skills/`); Letta discovers them in the agent's own `skills/` memory dir (or project/global skills dirs). So a cross-platform skill must be **written twice**, once in each format, tailored to each agent's role. On the Letta side the authoring reference is the `creating-skills` skill (what psnvc uses); on the Hermes side it's `hermes-agent-skill-authoring`.

## `hermes -z` one-shot bridge wedge ≠ model outage (learned 2026-09-09)

forge's `hermes -z` (one-shot, reached via the docker→nsenter→exec bridge) can return `API call failed after 3 retries: Connection error` while the model/provider are **perfectly healthy** — prove it by running `bash talk.sh --forge` interactively on the host, which answers instantly.

**The correct diagnostic order for "Connection error after 3 retries":**
1. **FIRST — test the model interactively, not just the one-shot.** `bash talk.sh --forge` (or `<name>`) from the host. If the interactive session answers fine, the model/provider/fleet are all healthy and you have a **bridge-specific wedge**, not an outage.
2. curl the model host from the pod → 401 = egress fine (only proves egress, NOT "model up").
3. Test a sibling's one-shot → if it also fails, that's a *bridge* symptom (all agents use the same bridge), NOT proof of a fleet-wide outage.
4. `kubectl rollout restart deploy/sudo-<name>` — cheap, try it, but a failure here still doesn't prove an outage.

**The load-bearing rule: a `hermes -z` one-shot that returns "Connection error" is a BRIDGE problem until the interactive `talk.sh` path is also shown broken. Re-run the one-shot exactly as [[skills/cross-host-execution/SKILL.md]] documents it before assuming anything heavier.**

Also: when the build is dispatched with `nohup ... > log 2>&1 &`, the log starts at **0 bytes** and only fills as forge writes — so a freshly-truncated 0-byte log is a healthy "started clean" signal, and a lingering old `Connection error` line in a log was what made monitor_2 false-positive repeatedly. When re-arming a monitor after clearing the log, grep for a *fresh* error against the truncated file, not a stale line.
