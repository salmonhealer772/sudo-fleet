## The multi-engineer meta (2026-09-28 — the NEW direction for the fleet build)
The operator surfaced a new meta for the fleet build while forge was mid-job on the pytest suite: **"one Letta planner, N engineers on hand, fire-and-forget dispatch."** His reasoning, verbatim-ish: "the runs just keep getting longer and longer… the agents are damn good but we should spec a different thing and dispatch a whole nother engineer and forge might still be going."

The shape: **one planner routes work to a *pool* of engineers (forge + forge-2 + forge-3…), not a single serial pipe.** When one engineer is still going on a long job, the planner specs a *different* thing and hands it to a *free* engineer — the planner's job stops being "wait for my one engineer" and becomes "route work to whichever engineer is free." This is the *why* behind the glimor/router work: a fleet that can hold multiple engineers is exactly what makes "don't block on one long run" possible.

**The discipline that makes N engineers work without recreating the overlapping-dispatch mess** (this session's core mistake — three `hermes -z` dispatches stacked on the *same* agent because the agent kept reading "live PID in `ps`" as "done"): each engineer **owns exactly one job at a time**, and the planner tracks busy/free by **result file**, never `ps`. Concretely the fleet wants: a **roster of engineers** with known busy/free state; dispatch to a **free** engineer tagged with a job id; a **no-double-dispatch guard** (if engineer X has a live job, send the next one to Y, not X again). This is the existing `message-agent` sender-side discipline (sequential per-recipient) extended to "route across a pool, one-in-flight each." Status: **direction only, NOT yet spec'd into the repo.**

## The steering law (2026-09-27) — agents are STORED, never memory-only
This is the load-bearing precondition, elevated above the promise list. An agent that lives only in memory (pod/PVC/live process) is an agent you can lose. Every agent exists as a **"glimor"** — the ENTIRE agent (setup + persistent state), auto-updating **once a save directory is given**. Save is not a manual backup you remember; it's the state the agent lives in. "Running" is a temporary view of a *stored* agent. Operator's analogy: "storage isn't the point of the car, it's the steering wheel that had better damn work."

## Cross-fleet forking (2026-09-27) — glimors are source-agnostic seeds
A glimor is both (a) the auto-updating stored state of *a* living agent (steering law) AND (b) a portable **seed** you fork from. Point any fleet's router at *where glimors live* (a path/address/source fleet — mechanism irrelevant to the vision), tell it "make N," and it spawns **N independent copies** — each copy, from the moment it's spawned, is its own agent and *itself* becomes a glimor that auto-saves in the **target fleet's own save directory** (does not write back to source). Independent, NOT linked/tied. The word "copy" was the tell — operator confirmed Option A ("copies are their own people") with "don't overthink it" spirit. Source stays put as the template for future forks.

## The mandatory piece: `save <name>` / `pull <name>`
This is the load-bearing requirement, refined by the operator 2026-09-27:

- **Save = a complete agent identity package** — BOTH the definition (persona.md / SOUL.md / config.yaml / model / ports) AND full state (memory, conversation history, PVC contents). One bundle.
- **It is printable** — you can render the package as a human-readable snapshot of "what is this agent, right now."
- **It is living** — the package **updates as the agent is used**; save isn't a one-time snapshot, it stays current, and `pull` restores the *latest* package wholesale. The save tracks the agent's ongoing identity + state.

- **`pull <name>`** restores the complete package — definition + full state — on any instance, so an agent survives fleet moves intact (same agent, mid-conversation, on the next box).
- Both must be **one or two commands**, stored in the host VM directory.
