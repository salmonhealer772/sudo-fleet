- The gateway (PID 161, `hermes gateway run --replace`) is ALWAYS alive — that's the doorbell, NOT forge thinking. Never read gateway-alive as forge-working.
- My `hermes -z` dispatches sent through `kubectl exec` wrapped in a **120s-capped Bash** die the instant the Bash times out — `kubectl exec` tears down the child. What's left in `ps` is a zombie half-job (looping on `ls`/`find` recon over fabean SSH), which I then misread as "still building." A process in the table with 0 output and no result file = DEAD, not working.
- The fix is stupidly simple and I kept missing it: the ONE clean command documented in talk-to-my-engineer — `kubectl exec -i deploy/sudo-forge -- hermes -z '<prompt>'` through the docker-socket bridge with the three `inf` env vars. It answers inline, instantly. Everything else I did (nohup &, base64 staging, process forensics) was invented wrapping that the skill already warned against.
- The decisive tell the operator used: `ps -ef | grep forge` on the host returning ONLY the grep line = forge not running, full stop. I argued with it via pid-namespace theories instead of accepting the process list as authoritative.
- New hard rule, replace any prior "check process" instinct: **forge is "running" only if I have actually sent `hermes -z` a message and read its reply in THIS session.** Zero-ambiguity test = does `hermes -z "say hi"` return "Hi." If yes, go. If no, `kubectl rollout restart deploy/sudo-forge` then send ONE plain message. No backgrounding. No monitor. No forensics for a simple hi.

**Don't pile up overlapping `hermes -z` dispatches — they OOM-kill the forge pod (exit 137) and come back empty (2026-09-27, the rabbit build).** During the rabbit build I fired many re-dispatches back-to-back (bash_238/239/240/…), and nearly every one came back `exit code 137` (OOM-killed) or an empty result file — because the concurrent `hermes -z` sessions stacked up inside forge's pod and blew past its memory limit. The tell: a dispatch "completes" with exit 137 or a 0-byte result file that never gained output. The fix is the same discipline as the other forge failures — **ONE clean dispatch at a time, wait for it to land (read the result file / check the process), before sending the next** — not a flurry of parallel re-dispatches that choke the pod and return nothing. When I catch myself spinning through many re-dispatches, stop, restart forge clean (`kubectl rollout restart deploy/sudo-forge`), and send a single focused message.

**THE SIGNAL OF "DONE" IS THE RESULT FILE, NOT THE PROCESS (2026-09-28, the pytest-tests dispatch — the overlapping-dispatch trap replayed exactly).** While dispatching forge to write pytest test files, I flailed for several turns: I kept running `ps aux | grep hermes`, seeing a live `hermes -z` PID (or its climbing CPU value), and concluding "forge is working" — when the true test is "did the result file land?" (`/opt/data/pytest-tests-result.md` or the task's output file). Because I fired a new full dispatch every time the operator said "ping" / "send the work" / "dispatch," I stacked THREE concurrent `hermes -z` processes (PIDs 622/1045/1530) all doing the same job, racing each other and dropping a junk `.venv` into the output dir. The sharpenings:
  1. **"Done" = the result/output file exists and has content.** A live `hermes -z` PID in `ps` is only evidence the job *started*, never that it *finished*. Check the RESULT FILE, not the process list, before declaring any state.
  2. **Before sending any new dispatch to forge, FIRST check** `ps aux | grep hermes | grep -v gateway | grep -v mcp_server | grep -v watch` inside the pod. If a `hermes -z` PID is already alive and advancing (CPU time climbing), DO NOT send another — the job is already running. Only dispatch the next one after the previous has produced its result file or been killed.
  3. **When the Bash tool's 120s cap severs the `kubectl exec` pipe**, a foreground `hermes -z` (with the `inf` timeout vars) survives as an orphaned-but-STILL-RUNNING process — DIFFERENT from the nohup backgrounding failure (which dies at the model call with "API call failed … Connection error"). Use the Bash tool's `timeout` parameter (e.g. `600000` = 10 min) to keep the pipe alive the whole time instead of relying on orphan survival.
  4. **For a LONG-RUNNING loop/grind job, have forge write its result to a FILE, not rely on inline stdout (2026-09-29, the sudo-fleet "forge owns the loop" job).** When I dispatched forge on a long wipe→bootstrap→fix→repeat loop, its inline report was lost to the 600s Bash cap — the `hermes -z` process ended cleanly but no result file was written, so forge's final account of "where iteration 4 stalled" evaporated into the severed pipe, and I had to re-dispatch a separate "write your current status to `/opt/data/loop-status.txt`" recovery message just to recover the story. The fix: for any multi-iteration or long-running forge job, include in the brief a directive to **write the final status/result to a named file** (`/opt/data/<task>-status.txt` / `<task>-result.md`) so the report survives the pipe regardless of timeout — then I read the file directly (`wrote it to a file so it can't be lost again`). Inline stdout is fine for a quick "say hi," but not for a job that legitimately outlives the Bash tool's cap. This is the same discipline as the ClawHub `agent-orchestrator` skill the operator had me find and adopt (2026-09-29, "find a skill for prompting your engineer effectively"): **write explicit success criteria into the brief, use file-based I/O instead of stdout, and keep a named status file that the reviewer (me) checks** — not a severed-pipe inline report.

**Delegate the whole grind as ONE self-contained loop, not drip-fed fixes — "forge owns the loop" (2026-09-29, corrected "my prompting forge a lot").** When a build keeps failing on a freshly-wiped box, the operator wants a single dispatch where forge drives the *entire* cycle itself: **wipe → run the contract exactly → find the exact break → fix in the repo → commit+push → repeat — until it completes clean with zero manual steps** — and I only report when it lands a clean end-to-end run (or needs something only he can provide), no narrating intermediate guesses. forge pushes a commit EVERY iteration, so progress is durable and I verify convergence from the git log instead of `ps` snapshots. This is the practical execution of "don't drip-feed forge partial theories across turns" — instead of me repro-ing a failure and dispatching one fix at a time, I hand forge the loop and the success criterion once, and it converges on its own.
